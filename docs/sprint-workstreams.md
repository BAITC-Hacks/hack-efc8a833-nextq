# Параллельные дорожки спринтов

Текущая работа — релиз City Lab по [контракту](design/release-city-lab.md). Спринты 1–3 ниже сохранены как история распределения задач: базовый раунд, события, Docker и Kubernetes уже интегрированы. Старые названия веток и задания не являются указанием создавать их повторно.

| Релизная дорожка | Граница | Результат |
| --- | --- | --- |
| Модель | `src/data/city-cases.ts`, `src/domain/evaluate-city-case.ts` | Датасет astana-1, четыре кейса, лаги, синергии, штрафы и рекомендации |
| AI и API | `src/infrastructure/cases`, `src/app/api/cases` | Генерация, подписи, серверный расчёт и анализ |
| Интерфейс | `src/components/city-lab`, главная и `/sandbox` | Каталог, рабочее место, сохранение, сравнение, экспорт |
| Интеграция | 3D, browser tests, зависимости, CI, docs, runtime | Полный проверяемый релиз и единый merge |

В каждом спринте три владельца работают по отдельным границам: Дима — модель и backend, Айым — проверяемость и инфраструктурный код, Сабина — интерфейс и пользовательские материалы. Файлы, принадлежащие другой дорожке, меняются через контракт и review. Перед стартом очередного спринта все ветки обновляются от последнего интегрированного коммита.

## Новые задания агентам — спринт 3

Каждый агент начинает с `git fetch origin`, обновляет `main` и создаёт собственную ветку от актуального `origin/main`. Айым работает в `feat/ayim-k8s-release`, Сабина — в `feat/sabina-release-guide`. Агент выполняет задачу целиком: изменения только в своей дорожке, профильные проверки, коммиты под Git-учётной записью участника без фиктивного co-author, push своей ветки, создание PR в `main`, ожидание CI, исправление замечаний, merge PR после успешных проверок и удаление своей ветки на origin. Перед merge агент проверяет, что `main` не ушёл вперёд; если ушёл — обновляет ветку от `origin/main`, повторяет проверки и только затем сливает. Общие файлы меняются через PR, секреты и персональные ключи не коммитятся.

### Айым — Kubernetes и проверка поставки

Ветка: `feat/ayim-k8s-release`. Добавить в `deploy/k8s/` Deployment и Service для приложения, readiness/liveness probes, безопасные requests/limits, непривилегированный контейнер и ConfigMap-шаблон для несекретной конфигурации. Образ и порт брать из Docker-контракта, который Дима добавит в `main`; секреты NVIDIA описать как ссылку на внешний Kubernetes Secret, не задавая значения. Добавить автоматическую проверку манифестов и команду deployment smoke-check, включить её в CI и описать запуск в `docs/testing.md`. Не менять приложение и Docker-файлы. Проверить манифесты локально доступным валидатором, CI, тестами и lint; явно указать ограничения, если в окружении нет Kubernetes-кластера.

### Сабина — инструкция запуска и хакатонная подача

Ветка: `feat/sabina-release-guide`. Создать `docs/deployment.md` с чистым сценарием запуска через Docker и развертывания опубликованного Kubernetes-комплекта Айым: требования, сборка/запуск, настройка env, проверка главной страницы и `/api/challenge`, остановка и типовые ошибки. Дополнить `docs/demo-script.md` двухминутной демонстрацией пяти решений, районной визуализации и события с тремя AQoL-состояниями; создать краткую структуру презентации в `docs/presentation.md`. Использовать только реально доступные команды и имена ресурсов из `main`, не менять production-код или манифесты. Проверить инструкции на чистом checkout насколько позволяет окружение и пометить только те шаги, которые требуют опубликованного образа или кластера.

## Передача и авторство

1. Владелец задачи создаёт ветку от последнего интегрированного коммита и ограничивает изменения назначенными файлами.
2. Изменения в общие контракты сначала описываются в pull request; соседние дорожки продолжают работу по текущей версии.
3. Перед передачей запускаются `pnpm test`, `pnpm lint`, `pnpm build` и профильные проверки дорожки.
4. Каждый участник создаёт коммиты под собственной настроенной Git-учётной записью. Другой участник не подменяет автора и не добавляет фиктивный co-author.
