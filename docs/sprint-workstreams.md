# Параллельные дорожки спринтов

В каждом спринте три владельца работают по отдельным границам: Дима — модель и backend, Айым — проверяемость и инфраструктурный код, Сабина — интерфейс и пользовательские материалы. Файлы, принадлежащие другой дорожке, меняются через контракт и review. Перед стартом очередного спринта все ветки обновляются от последнего интегрированного коммита.

## Спринт 1 — игровой сценарий

| Дорожка | Ответственный | Код и документы | Контракт / статус |
| --- | --- | --- | --- |
| A — симуляция и сервер | Дима | Синтетический каталог, доменный расчёт, AQoL, валидация бюджета, HTTP API, NVIDIA-адаптер | `ScenarioResult`, `POST /api/scenario`, `narration.ready/unavailable`; основной функционал реализован |
| B — качество и воспроизводимость | Айым | Добавить проверки инвариантов каталога в `src/data/city-v1.test.ts`, включить их в `pnpm test`, настроить `.github/workflows/verify.yml` для Node 22 и pnpm, описать проверки в `docs/testing.md` | Не менять каталог/движок/API; тестировать опубликованные типы и правила |
| C — городской штаб и демо | Сабина | UI пяти решений и отчёт; дополнить `docs/demo-script.md` пошаговой демонстрацией бесплатного, bus-priority и полного сценариев, бюджетом и ожидаемым AQoL | Клиент отправляет только версии и ID решений; UI уже разрабатывается в дорожке C |

Параллельный старт: дорожка A фиксирует стабильный доменный/API-контракт; B может писать независимые тесты и CI; C использует контракт для UI. В текущем спринте общие файлы `package.json` и `README.md` меняются после согласования с владельцем дорожки A.

## Спринт 2 — сравнение и городские последствия

| Дорожка | Ответственный | Код и документы | Контракт / граница |
| --- | --- | --- | --- |
| A — сценарии и правила | Дима | Версионированные городские события, детерминированное перераспределение бюджета, сравнение и серверные рекомендации | Сначала опубликовать схемы `CityEvent` и `ScenarioComparison` |
| B — проверка модели | Айым | Тесты событий, сравнения, лимитов и воспроизводимости; обновить методику синтетических допущений в `docs/model-assumptions.md` | Отдельные тестовые файлы; не менять production-логику дорожки A |
| C — аналитика и подача | Сабина | Визуализация изменений районов, сравнение сценариев рядом, история последствий и экспорт краткой презентации | Рисовать только поля из `ScenarioComparison`; компоненты в `src/components/comparison/` |

## Спринт 3 — воспроизводимый запуск

| Дорожка | Ответственный | Код и документы | Контракт / граница |
| --- | --- | --- | --- |
| A — приложение и контейнер | Дима | Health endpoint, multi-stage Docker image, production runtime и серверная конфигурация | До старта согласовать image name, порт, health path и env-переменные |
| B — поставка и проверки | Айым | Kubernetes Deployment/Service, probes, ресурсы, Secret/ConfigMap-шаблоны и deployment smoke-check в `deploy/k8s/` | Использовать согласованный контракт образа; секреты не коммитить |
| C — запуск и презентация | Сабина | `docs/deployment.md`, быстрый сценарий демо, инструкции по проверке UI и краткая презентация проекта | Документация запуска проверяется на чистом checkout и опубликованном образе |

## Передача и авторство

1. Владелец задачи создаёт ветку от последнего интегрированного коммита и ограничивает изменения назначенными файлами.
2. Изменения в общие контракты сначала описываются в pull request; соседние дорожки продолжают работу по текущей версии.
3. Перед передачей запускаются `pnpm test`, `pnpm lint`, `pnpm build` и профильные проверки дорожки.
4. Каждый участник создаёт коммиты под собственной настроенной Git-учётной записью. Другой участник не подменяет автора и не добавляет фиктивный co-author.
